# Проверка в dev-кластере

Используйте отдельный тестовый namespace, а не рабочие workloads. Для первой
проверки можно направить generic webhook в тестовый HTTP-получатель.

1. Установить chart с dev-профилем, дождаться /readyz и проверить логи.
2. Создать Deployment с `sh -c 'echo failed >&2; exit 1'`. Проверить алерт
   после порога/устойчивого CrashLoop, наличие предыдущих логов и поля logs.
3. Удалить один падающий Pod. Проверить, что новый Pod того же Deployment
   не обходит repeat-interval.
4. Повторить с prod и новым Deployment UID: первое падение уведомляет сразу.
5. Выполнить rollout restart исправного Deployment: crash-уведомлений нет.
6. С exclude Job/CronJob создать падающий Job и CronJob: их поды не уведомляют.
7. Исправить образ/command: после стабильного восстановления приходит resolved.
8. Временно возвращать 429/500 от тестового получателя: доставка повторяется;
   работающий второй получатель не получает дублей из-за первого.
9. Обновить config ConfigMap или Secret: Reloader перезапускает Pod;
   сохранение state ConfigMap не перезапускает его.
10. Проверить Telegram сначала отключённым (Secret не нужен), затем включить
    с отдельным тестовым чатом. Проверить topic ID и ограничение текста.
11. Перезапустить k8s-alert: активные инциденты и cooldown восстанавливаются.
12. На время запретить доступ к Kubernetes API: потеря наблюдения не даёт
    ложного resolved. После восстановления связи нужен новый healthy period.

Результат этих сценариев в реальном кластере пока не получен. Unit-тесты и
Helm-проверки не заменяют этот прогон.
